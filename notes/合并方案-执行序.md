# 合并方案 · 执行序与决策（对话线 + TRPG 线）

> 目标：characterCardStore 成为唯一人物卡/故事数据源；TRPG 能力作为独立开关挂在卡/Persona 上，默认关闭。
> 配套文档：`合并方案-逐文件拆解.md`（game.vue 拆组件 + 存储重键化的逐文件清单）。

---

## 一、五个运行期决策（Phase 0 必先定死）

### 决策 1：统一生成入口 = MessageProcessor
- 废弃 `gameAI.generateWithIntent`，TRPG 不再有第二条生成路径。
- TRPG 只是往 `MessageProcessor.send` 里多注入一个"状态块" + 一个 intent 钩子。
- `game.vue` 里的 `callAIServiceStream` 逻辑全部迁入 `chat.vue`（它已在用 `processor.send`）。

### 决策 2：统一世界书 = WorldInfoEngine + characterCardStore.getLorebook
- 废弃 `lorebookManager.js`。
- **新增一个直查 API**（如 `characterCardStore.getLorebookEntryByKey(cardId, key)` / 或 WorldInfoEngine 加 `findEntryByKey`）—— 战斗 `getNPCDef` 需要"按键取条目"，而 WorldInfoEngine 只有"扫描聊天+注入"，没有直查。

### 决策 3：统一宏 = 升级 VariableEngine
- 支持 `{{name::arg1::arg2}}` 参数语法（兼容清单 P0-4）。
- 注册 TRPG 宏：`{{hp}}/{{mp}}/{{san}}/{{scene}}/{{story}}/{{trust::name}}/{{flag::name}}/{{char}}/{{user}}/{{persona}}`。
- 废弃 `macros.js`（其 `{{char}}/{{user}}/{{hp}}` 等语义并入 VariableEngine）。
- **这是硬前置**：human-despair 迁移过来的世界书文本/systemPrompt 里带着 `{{scene}}/{{hp}}`，当前 VariableEngine 解析不了。

### 决策 4：TRPG 上下文注入机制 = 一条固定 identifier 的提示项
- identifier 定为 `trpgStatus`（system 消息），内容 = 六维属性 + HP/MP/SAN + 战斗摘要 + 任务进度。
- 由 `modules.stats/adventure/combat` 开关驱动是否生成；`stats=false` 则不注入六维。
- **务必与兼容清单 P0-1（marker 填充）走同一条注入机制**，避免二次返工。

### 决策 5：intent 钩子位置 = MessageProcessor.send 内"输入正则之后、世界书扫描之前"
- 仅 `intentDetection` 开启时运行 `intentParser`；产物（ATTACK/MOVE/TALK_TO 等）回传给 combat 触发。

### 决策 6：TRPG 运行时状态归属（新增，必须定）
- 合并后 HP/MP/背包/任务/信任度/flag 挂在**会话（conversation）**上，而不是全局 `GAME_STATE_*`。
- 建议：`conversationManager` 的 record 增加 `trpgState` 字段（或并入现有 `worldInfoState`/`localVariables` 同级），key 从 `cardId` 扩展为 `cardId + personaId`。

### 决策 7：moduleStore 字段去留
- 现行 `moduleStore` 有 `skills/music/lorebook` 三个字段不在新 modules 列表里：
  - `lorebook` → 常开，删开关；
  - `music` → 删；
  - `skills` → 并入 `stats` 或删（战斗技能已走 combat 内 `skillsDB`）。

### 决策 8：characterCardStore.update 必须深合并 extensions
- 现行 `characterCardManager.updateCard` 是 `Object.assign` 浅合并，切一个开关会把 `extensions.trpg.items/depth_prompt` 顶掉。必须做 `extensions` 深合并。

## 二、存储重键化清单（摘要）

| 文件 | 现行 key | 目标 key | 说明 |
|---|---|---|---|
| `utils/engine/stateManager.js` | `GAME_STATE_${storyId}_${characterId}` | 并入会话 `trpgState`，或 `TRPG_${cardId}_${personaId}` | 51KB，状态结构见逐文件清单 |
| `utils/storage.js` | 内部 `GAME_STATE_${storyId}_${characterId}` 助手 | 同步改 | 有 `STORAGE_KEYS.GAME_STATE='game_state'` 旧键 |

| `utils/character_info/character-manager.js` | `CHARACTER_LIST_KEY` + 每角色 key + `ACTIVE_CHARACTER_KEY` + lorebook key | 整体废弃，由 personaStore 取代 | 其函数迁 `utils/persona/trpgProfile.js` |
| `App.vue` + `story-select.vue` | `rpg_game_state`（globalData） | 废弃 | 旧全局游戏态 |

## 四、推荐执行顺序（修订版）

| Phase | 内容 | 退出条件 |
|---|---|---|
| **0** | 落定上表 8 个决策；列全重键化 + 死 utils 清单（本文件 + 逐文件清单） | 决策冻结 |
| **1** | 类型扩展（`extensions.trpg`、`personaStore.trpgProfile`）+ `characterCardStore.update` 深合并 + trpgProfile.js 纯函数迁移 | 类型/存储基础就绪 |
| **2** | 运行期接缝统一 + 最小垂直切片：`_characterForProcessor` 透传整卡 → PromptBuilder 加 `trpgStatus` 注入点 → MessageProcessor 加 intent 钩子 → 世界书加 `getEntryByKey` + parseCombatTag → combatManager.getNPCDef 改造。**用手工最小 TRPG 卡做冒烟** | 数值进 LLM、intent 触发、combat 标签解析 三者跑通 |
| **3** | human-despair 迁移脚本 + 拆组件接入 chat.vue（见逐文件清单）+ 用迁移卡端到端 | 背包/状态栏/骰子/战斗面板可用 |

> 关键改动点：原方案把"迁移"和"UI"排在运行期接缝之前、端到端验证放最后。这里改为 **Phase 2 用小卡先冒烟**（最早验证点），**Phase 3 再迁移+接组件**（拆组件依赖迁移后的卡才能联调）。

## 六、已确认决策（最终版，2025 执行依据）

以下均已与用户确认，全部采用推荐项：

1. **宏系统范围 = 最小可用版**：手写解析器，支持 `{{name::a::b}}` 参数 + 变量宏(get/set/inc/dec) + TRPG 宏(hp/mp/scene/flag) + 常用宏(random/roll/time)。暂不做 `{{if}}`/scoped/list 完整 AST（留待兼容性后期）。
2. **trpgStatus 注入 = PromptBuilder 的 marker 提示项**（identifier=`trpgStatus`），与 P0-1 同机制。
3. **TRPG 运行时状态归属 = 挂会话 conversation**（随 conversationManager 记录存），stateManager 逻辑迁纯函数/composable。
4. **旧存档 = 直接丢弃**，不做迁移脚本。
5. **战斗回合状态 = 持久化**，纳入会话存档。
6. **兼容 P0 = 顺带一起做**（宏升级=P0-4，trpgStatus 注入=P0-1）。
7. **moduleStore 的 skills 字段 = 并入 stats**；music 删除；lorebook 常开去开关。

无争议默认（已确认）：决策1 统一入口 MessageProcessor；决策2 统一世界书 WorldInfoEngine+直查API；决策5 intent 钩子在"输入正则后/世界书扫描前"；决策8 characterCardStore.update 深合并 extensions；组件沿用现有 4 个展示组件不重写。
