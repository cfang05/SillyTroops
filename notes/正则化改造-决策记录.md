## 2. 第一部分：流式输出体验

### 2.1 现状：两条路径，默认走慢的那条

| 路径 | 触发条件 | 现象 | 量级 |
|---|---|---|---|
| A. 假流式（打字机模拟） | 预设 `stream=false`（**当前默认**） | 全文生成完才逐字"念"，每字停 40–250ms | **约 10–12 字/秒**，600 字回复约 50–60 秒 |
| B. 真 SSE 流式 | 预设 `stream=true` | 上游速度正常，但每个 delta 触发全文重解析 + 整表重渲染 + 落盘 | 首字正常，中后段掉帧，长会话越用越慢 |

### 2.2 原因清单

| 优先级 | 问题 | 位置 |
|---|---|---|
| P0 | 默认未开真流式：`createDefaultPreset()` 为 `stream: false`，且导入时缺字段一律按 false 处理 | `defaultPreset.ts:170`、`PresetImporter.ts:33` |
| — | ⚠️ **勘误**：早前曾判断"两个内置预设没有 `stream_openai` 字段"，**该判断错误**（当时的检索工具在超大单行 JSON 上漏匹配）。实测 `st_preset/DSmamav1.8.json` 与 `DSthinkerV4-0902.json` **都带 `stream_openai: true`**。因此：**用内置预设时真流式是开的**；走假流式的只有"默认预设"与"导入时缺该字段"的情况 | 已由 node 复核 |
| P0 | 打字机每字一个 `setTimeout`，基础 60ms，标点后 120/200ms，换行后 300ms，再叠 ±20ms 抖动 | `MessageProcessor.ts:197-225` |
| P0 | 每个 delta 做一次全文 `parseBlocks`（O(n²)） + 全量数组替换 → 父组件重渲染整张消息表 | `chat.vue:538-544`、`:635-639`、`:21`、`:40` |
| P1 | 续写路径每个 chunk 同步写 localStorage（含序列化全部消息 + segments） | `chat.vue:470` → `conversationManager.js:74` |
| P1 | 续写结束后调用不存在的 `runtimeStore.forceUpdate()` → 抛错 → "停止"按钮不恢复、内容不落盘 | `chat.vue:478` |
| P2 | 生成结束时同步跑真 tiktoken 编码整段 prompt | `MessageProcessor.ts:144-163`、`tokenizer.ts:44-65` |
| P2 | `DEBUG_ENABLED = true` 恒开，每次发送打印全量 messages | `DebugLogger.ts:5` |
| P3 | 上下两条 fixed + `backdrop-filter: blur(14px)` 栏，下方内容每变一次就重算合成 | `chat.vue:738-740`、`:830-831` |
| P3 | SSE 每 delta 回调全量累加字符串而非增量 | `client.js:523` |
| P3 | `reasoning_content` 与 `content` 混进同一缓冲区，无法折叠 | `client.js:520` |

### 2.3 方案档位与效果预测

假设 600 字回复、上游生成约 20 秒：

| 方案 | 首字出现 | 末字出现 |
|---|---|---|
| 现状 | ~20s | ~74s |
| 2+3+6（不碰流式开关） | ~20s | ~33s |
| 1+3+6（推荐组合） | ~1–2s | ~20s |

- **1** 默认开真流式（代价：正则过滤需分级；小程序端退化为整段出现）
- **2** 打字机改为按时间片批量吐字（40–60 字/秒）
- **3** chunk 节流（每 40ms 合并一次解析与渲染）
- **4** 抽 `MessageItem.vue` 子组件，只重画变化的那条消息
- **5** 续写改为"生成期间不写盘，结束写一次"
- **6** 修 `runtimeStore.forceUpdate()` 崩溃
- **7** 生成期间临时关闭毛玻璃

## 3. 第二部分：正则系统改造（D1–D4）

### 3.1 酒馆一致的三个要件

| 要件 | 酒馆 | 本项目现状 |
|---|---|---|
| ① 正则可产出样式标记（HTML） | 消息由 showdown 渲染为 HTML | ❌ 渲染层是 `<text>` 树；HTML 唯一出口是沙箱 iframe |
| ② 原文 / 显示文本分离 | `mes` 存原文；`markdownOnly` 只在渲染时跑；`promptOnly` 只在拼 prompt 时跑 | ❌ 正则一次性应用，结果同时用于显示/存档/上下文 |
| ③ CSS 出口 | 设置内有 Custom CSS | ❌ 无入口，样式硬编码 |

地基已具备：`security.ts:12-24` 的 `sanitizeHtml()` 白名单**已允许 `style` 与 `class`**，DOMPurify 已是依赖。

### 3.2 硬编码 → 正则 迁移对照（D1）

| 现在 | 位置 | 并入后 |
|---|---|---|
| 引号状态机识别台词 | `BlockParser.ts:125-161`（引号表 `:9-10`） | 正则 `“([^”]+)”` → `<span class="say">$1</span>` |
| "≤5 字且无标点不算台词"门槛 | `BlockParser.ts:140-144` | 更精细的 pattern 近似，或直接取消 |
| 台词另起一行 | `BlockRenderer.vue:126-130` | CSS `.say { display: block }` |
| 台词金色斜体 | `RichText.vue:33-36`、`BlockRenderer.vue:131-136`、`App.vue:368` | CSS `.say { color: oklch(82% .13 95); font-style: italic }` |
| 两侧重画直引号 | `BlockRenderer.vue:50/53` | 正则决定是否保留 |
| 台词内抹掉换行 | `BlockParser.ts:157` | `replaceString` 不插 `\n` 即可 |

**正则做不到的**：配对/奇偶/跨行判断。实际影响很小。

### 3.3 真流式下的体验（已分析）

结论：**与现状几乎一致** —— 闭引号到达时"整句啪地跳一下"（变色 + 换行 + 顶开下文）。**不是正则引入的退化**，现状硬编码同样是等闭引号才 push `speech` 节点。

| 跳动 | 严重度 | 原因 |
|---|---|---|
| A 字形/颜色突变 | 中 | 一行文字整体变金色斜体 |
| B **换行引起位移** | **最难受** | `display:block` 生效瞬间该句独占一行，下方内容被顶下去 |
| C 引号被改写 | 视写法 | 正则顺手替换引号 |

消除手段：①**未闭合容忍**（追加 `“([^”]*)$` → 同一个 class，闭合那刻视觉零变化，成本仅多一条正则）；②旁白保持块级（现状 narrative 已是每句一块）；③改布局的脚本延后到完整消息再跑。

流式化必备防护：**限流**（只跑未冻结的尾部）+ **超时熔断**（灾难性回溯）+ **`sanitizeHtml`**（XSS）。

### 3.4 已发现的开关失效问题

`RegexScriptEngine.ts:147-155` 的生效判定依赖 `isMarkdown` / `isPrompt`，但：

| 调用点 | 传了什么 | 后果 |
|---|---|---|
| 输入侧 `MessageProcessor.ts:67`（placement=1） | 只传 `vars` | **勾"仅 Prompt"的脚本永不执行** |
| 输出侧 `MessageProcessor.ts:132`（placement=0） | 只传 `vars` | **勾"仅 Markdown"的脚本永不执行** |
| 世界信息 `PromptBuilder.ts:107-111`（placement=2） | 传了 `isPrompt: true` | ✅ 唯一正确路径 |

可验证后果：项目自带示例脚本 `st_regex/regex-DSmama.json` 是 `promptOnly: true` + 输入侧 → **一行都不生效**。

> 这正好解释了"**内置正则没有生效**"的观察：内置正则就是这一条。D7 决定先删除内置资源，但**该开关 bug 仍需修复**，否则用户自己导入的 `markdownOnly` / `promptOnly` 脚本同样会失效。

## 4. 第三部分：原文 / 显示文本分离（D5）

### 4.1 定义

**存档只存原文；"好看的排版样子"在渲染那一刻现算，不落盘。**
类比 Markdown：存的是 `# 标题`，看到的是大号加粗，加粗不会被写回文件。

### 4.2 现状链路与三个后果

```
模型返回原文
  → MessageProcessor.ts:132 正则跑一次（结果 finalReply）
  → chat.vue 存进 content/swipes      ← ① 存档
  → parseBlocks 渲染                  ← ② 显示
  → toChatHistory() 读 content 发模型  ← ③ 下一轮上下文
```

一旦正则产出样式标记：① 编辑消息看到的是 HTML；② HTML 被当作"AI 上次的发言"发回模型，**模型会开始模仿输出标签（污染自我扩散）**；③ 若正则是"删除类"，被删内容从未入档，**不可恢复**。

### 4.3 分离后的分工（= 酒馆三个开关的真实语义）

| 脚本类型 | 作用对象 | 落地 |
|---|---|---|
| 普通（两个开关都不勾） | **原文** | 真的改写消息本体（进存档、进上下文） |
| 仅 Markdown（`markdownOnly`） | **只影响显示** | 台词上色应属此类；存档与上下文保持原文 |
| 仅 Prompt（`promptOnly`） | **只影响拼 prompt** | 存档存原文，发模型时临时变形 |

### 4.4 影响面清单

| 功能 | 现状 | 分离后 |
|---|---|---|
| 编辑消息 | 编辑 `content` | 编辑原文，显示自动重算 |
| swipes 备选回复 | 存正则后文本 | 存原文 |
| 续写前缀 | 拿 `content` | 拿原文（否则把 HTML 喂给模型） |
| 导出/复制 | `content` | 原文 |
| token 统计 | 正则后文本 | 原文（口径更准） |
| `segments` | 与消息一起入档 | 降级为渲染缓存，只能由原文派生 |
| 流式渲染 | 对累积文本 parseBlocks | 对累积**原文**先跑"仅 Markdown"正则再解析 |

### 4.5 不可逆的坑

老存档的 `content` 已被历史正则处理过：替换/加装饰类可清理还原；**删除类**内容无法恢复 → 需在改造说明中提示。

## 5. 第四部分：历史记录存储与上下文（新增讨论）

### 5.1 现在存在哪里

| 项 | 事实 | 位置 |
|---|---|---|
| 介质 | **浏览器 localStorage**（`uni.setStorageSync` 在 H5 落地为 `window.localStorage`） | `storage.js:32-40` |
| 键名（按用户隔离） | `u_{userId}_conversation_list`、`u_{userId}_conversation_{cardId}` | `userScope.js:16-19`、`conversationManager.js:15-16` |
| 内容 | 整份对话（全部 messages，**每条消息还带已解析的 `segments` AST**、swipes、trpgState、worldInfoState） | `conversationManager.js:57-81` |
| 写入 | 每次保存把整份 JSON 序列化 + 同步写盘；随后 `_upsertListItem` 又读一次列表再写一次 | `conversationManager.js:74`、`:83-99` |
| 读入 | 打开对话时**一次性全量**塞进内存响应式 store | `chat.vue:271-284` |
| 服务端 | **完全没有对话存储**：`migrate.js` 只建 accounts / usage_stats / usage_daily / login_events；`server.js` 路由只有 auth / admin / stats / test-api / proxy | `migrate.js:15-71` |

→ 结论：**对话只存在于这台设备的这个浏览器里**，换设备、清缓存即丢。

### 5.2 体积与失败模式（真隐患）

- 同源 localStorage 配额通常 **5MB 左右**（浏览器 5–10MB），且**全站共享**：角色卡 + 世界书 + 预设 + 每个角色的对话存档挤在同一配额。
- 注意：预设是**一个键装全部预设**（`presetStore.ts:12/87`），而项目自带预设 `st_preset/DSthinkerV4-0902.json` 就有 **1.3MB**。
- 单条消息的存档体积 ≈ 原文的 **3~6 倍**（`segments` AST 一并序列化）。
- **顶爆配额时的行为**：`uni.setStorageSync` 抛错 → `conversationManager.save` 内 try/catch 吞掉并只 `console.error`（`conversationManager.js:75-78`）→ **返回 false 但所有调用方都忽略返回值** → **用户无任何提示，存档静默停在上一次成功状态**。

### 5.3 为什么"长"会伤浏览体验（4 个机制）

1. **首屏全量渲染**：`v-for` 渲染全部消息，每条消息内部还有多个子节点；DOM 节点数随历史线性增长。
2. **整页滚动**：为确保只有一条滚动条，页面取消了内层 scroll-view 改用系统整页滚动（`chat.vue:16-19` 注释），意味着**整页高度 = 全部历史高度**，浏览器要一次性完成全部布局。
3. **流式期间全表重渲染**：每个 chunk 换新数组 + 父组件 render 读每条消息的 `content` → 历史越长，每个 token 的渲染成本越高。
4. **每次保存全量重写**：同步阻塞主线程，历史越长越卡（与 2.2 的 P1 同源）。

### 5.4 prompt 侧：完全没有裁剪（另一个隐患）

- `PromptBuilder` 把 `chatHistory` **原样全部 push**（`:215-227`），**没有任何按 token 预算裁剪历史的逻辑**。
- `maxContext`（默认 4096）**只用在世界书预算**（`PromptBuilder.ts:88` → `WorldInfoEngine.ts:227-235`），不参与历史裁剪。
- 后果：历史越长，每轮 prompt 越大 → 首字延迟变长、费用变高、最终**超出模型上下文窗口直接报错**（用户会以为是"随机报错"）。

### 5.5 酒馆的做法（三个支柱，分层解决三层问题）

| 层面 | 酒馆做法 | 解决什么 |
|---|---|---|
| 存储 | 对话是**服务端磁盘上的文件**，一行一条消息（`.jsonl`）；一个聊天一个文件；"检查点/分支"= 克隆文件 | 不受浏览器 5MB 限制；文件写入异步，不阻塞界面 |
| 渲染 | **只加载最近一批消息**（Chat Truncation，默认约 100 条，随版本有差异），顶部"显示更多消息"逐批加载更早的 | DOM 节点数恒定，长聊天不拖慢浏览 |
| 上下文 | prompt 侧按 **token 预算**裁剪：`openai_max_context` + 聊天历史深度 + `/hide`（单条消息从上下文隐藏） | 每轮请求体量可控，不超窗口、不越用越贵 |

参考来源：[酒馆中文文档·聊天文件管理](https://sillytavern.wiki/usage/core-concepts/chatfilemanagement/)（说明聊天以 `.jsonl` 文件存储、可导出/导入、检查点=克隆文件）、[DeepWiki · Chat Storage and Persistence](https://deepwiki.com/SillyTavern/SillyTavern/5.2-vector-search)。另有社区分支把"聊天文件分段存储优化"列为改进项（[zhaiiker/SillyTavernchat](https://github.com/zhaiiker/SillyTavernchat)），侧面说明长聊天在酒馆同样是性能痛点。

### 5.6 可参考的替代方案对比

| 方案 | 容量 | 阻塞主线程 | 跨设备 | 改动量 | 备注 |
|---|---|---|---|---|---|
| A 维持 localStorage（现状） | ~5MB 共享 | 是（同步） | 否 | 0 | 迟早静默丢档 |
| B **只瘦身**：不存 `segments`、消息与元数据分键、保存防抖 | 余量 ×2–3 | 仍同步 | 否 | 小 | 立刻缓解，天花板仍在 |
| C **IndexedDB**（H5 专属，`#ifdef H5`） | 数百 MB | 否（异步） | 否 | 中 | 一条消息一条记录，天然支持"只读最近 N 条"，与分页渲染配套 |
| D **服务端存储**（参考酒馆） | 几乎无上限 | 否 | 是 | 中大 | 项目已有 Express + Postgres，`migrate.js` 建表模式现成；需解决鉴权、配额、离线场景 |
| E 混合：服务端为准 + 本地缓存最近 N 条 | 上限高 | 否 | 是 | 大 | 最接近酒馆，工程量最大 |

**推荐路线（已按 D6 收敛）**：**先本地优先**——B 立即做（属于已定位问题的修复）→ **C（IndexedDB）作为 H5 主方案**，配套"只渲染最近 N 条"→ D/E（服务端、跨设备）**后置**，待本地方案跑稳后再逐步加入。

### 5.7 渲染侧参考（最直接改善浏览体验）

采用酒馆的**分批加载**：初始只渲染最近 N 条（建议 50–100），顶部"显示更多"或滚动到顶自动加载下一批。
前提是数据层能"按范围取消息"（IndexedDB / 服务端天然支持；localStorage 也行，只是省不掉解析与存储成本）。
与流式优化的关系：**这是同一个问题的两端** —— "只渲染最近 N 条"能顺带把"每 token 全表重渲染"的成本砍掉。

### 5.8 存储占用清单（D6 补充调查）

用户设备上要装的东西远不止对话。全部挤在**同一个 ~5MB 同源 localStorage 配额**里：

| 数据 | 现在存哪 | 体积量级 | 备注 |
|---|---|---|---|
| **内置预设** | `u_{uid}_llm_presets`（**一个键装全部预设**） | **约 1.35MB**（`DSthinkerV4-0902.json` 1.3MB + `DSmamav1.8.json` 37KB） | ⚠️ `presetStore.load()` → `_loadBuiltinPresets()` **会自动把内置预设载入并 `_persist()` 落盘**（`presetStore.ts:94-124`）——**用户什么都没做就占掉约 1/4 配额** |
| 角色卡本体 | `u_{uid}_char_card_{id}` | 单卡数十 KB～**数 MB** | `avatar` 是 **base64 data URL**（`types/character.ts:174`） |
| 角色卡头像 | 内嵌在卡片的 `avatar` 字段 | 正常：512px JPEG ≈ 40–150KB；**异常：原图 base64，可能数 MB** | `CharacterImporter.ts:103-108`：缩略图生成失败的**回退分支直接存原图** |
| 角色卡世界书 | `u_{uid}_char_card_lorebook_{id}` | 数十 KB～数百 KB | 独立键，`characterCardManager.js:17` |
| 对话存档 | `u_{uid}_conversation_{cardId}` | 原文的 **3–6 倍**（含 `segments` AST） | 见 5.1 |
| 正则预设 / persona / 用户资料 | 各自键 | 小 | 可继续留 localStorage |

结论：**"本地存储"目前的天花板不是对话，而是"内置预设 + 角色卡（含 base64 头像）"**，而这两者都是用户一上手就有的。

### 5.9 本地优先（D6）的落地要点

**介质必须从 localStorage 换成 IndexedDB**，理由：容量数百 MB、异步不阻塞、**可按条读取**（天然支撑"只渲染最近 N 条"）。localStorage 是"一个键一整坨 + 同步"，装不下也读不动。

建议归属：

| 数据 | 建议介质 |
|---|---|
| 对话消息 | **IndexedDB，一条消息一条记录**（可按范围读） |
| 角色卡 + 世界书 | **IndexedDB**（大对象，可存 Blob） |
| 用户导入的预设 / 正则 | IndexedDB |
| **内置预设 / 内置正则** | **不落盘**（它们本来就是 `/assets/...` 的静态文件，`builtinAssets.ts` 每次 fetch 即可）→ **这一步直接释放约 1.35MB，改动极小、收益最大** |
| 设置、活跃 id 等小数据 | 可继续留 localStorage |

**架构建议（关键）**：定义统一存储接口（`get / set / remove / list / query`），先实现 `LocalAdapter`（IndexedDB）；将来加跨设备时只新增 `RemoteAdapter`（服务端），**业务代码不动**。否则"以后慢慢加跨设备"会变成全项目重写。

**本地优先必须配套的三件事**（否则迟早丢数据）：

1. **申请持久化存储**：`navigator.storage.persist()`，避免浏览器在磁盘紧张时自动清理（Safari 对非持久化站点存在"长期不访问即清理"策略）。
2. **配额监控**：`navigator.storage.estimate()` 查询用量，设置页显示"已用 / 上限"，接近上限时提示导出。
3. **导入 / 导出备份**：对话、角色卡、预设、正则都要能整体导出导入——本地存储随时可能被系统清掉，这是唯一的兜底（酒馆也是靠导出 `.jsonl` / 角色卡 PNG 兜底）。

> 一句话：**"先本地存储"可行，且现在就是本地；但要做的是"换介质 + 拆存储 + 停掉内置资源落盘 + 加持久化申请与备份"，而不是维持现状。**

### 5.10 prompt 侧 token 裁剪（Q8 详解）

**是什么**：在把消息发给模型**之前**，按 token 预算把聊天历史裁剪到能装进模型上下文窗口的程度。**只影响"这一次发出去的内容"，不影响存档**（与 D5 的"原文/显示分离"是同一个思路：存档是真源，发出去的是派生结果）。

#### 现状：完全没做

- `PromptBuilder.ts:215-227`：`chatHistory` **原样全部** push 进 messages，没有任何裁剪逻辑。
- `maxContext`（默认 4096）**只喂给世界书预算**（`PromptBuilder.ts:88` → `WorldInfoEngine.ts:227-235`），**不参与历史裁剪**。

#### 不做的三个后果

| 后果 | 说明 |
|---|---|
| **硬失败** | 历史超过模型上下文窗口 → 上游直接报错。用户会以为是"随机报错"，实际是聊太久了 |
| **成本线性增长** | 第 N 轮要把前面 N-1 轮全部重发一遍，token 费用随轮次累积 |
| **首字延迟变长** | prompt 越长，prefill 越慢，越聊越卡 |

#### 预算怎么划分

```
模型窗口上限 maxContext
  − 回复预留 maxTokens            （给模型写回复的空间）
  − 安全余量                       （防止估算误差撑爆）
  = prompt 预算
        ├─ 系统提示（main / 角色描述 / 性格 / 场景）
        ├─ 世界书（已有按百分比分配的预算）
        ├─ 作者注 / depth 注入
        ├─ 尾部指令（post_history_instructions / jailbreak）——必须留
        ├─ 本次用户消息 ——必须留
        └─ 剩余部分才给「聊天历史」
```

#### 裁剪算法（关键：从新往旧填）

1. **必留项先占位**：系统提示、尾部指令、本次用户消息——这些先扣预算。
2. **从最新一条历史往旧遍历**，逐条累加 token，直到预算用尽，更早的丢弃。
   （**不能**从最旧往新截断——那会把最有价值的近期上下文丢掉。）
3. **保持 user/assistant 成对**：裁剪后第一条不能是孤立的 assistant（部分 API 会拒绝）。
4. `first_mes`（开场白）通常位于历史最前，被裁掉是可接受的。

#### 与酒馆的对应

| 酒馆 | 说明 |
|---|---|
| `openai_max_context` | 上下文长度（总窗口） |
| `openai_max_tokens` | 回复预留 |
| 世界书「上下文百分比」 | 给世界书分配多少窗口 |
| Prompt Manager 里的 **Chat History** 条目 | 可禁用、可设深度 |
| 「上下文消息条数」模式 | 按条数裁剪的简化版 |
| `/hide` | 把单条消息从上下文中剔除（不删消息） |

#### 容易被忽略的工程细节

| 细节 | 说明 |
|---|---|
| **token 数要缓存** | 每条消息算一次存起来复用；现在是每轮把全部历史拼起来重算（`MessageProcessor.ts:144-163`） |
| **计数口径** | 优先用上游返回的 `usage` 真值；拿不到用启发式估算（见 2.2 P2 与 `tokenizer.ts`） |
| **必须可观测** | UI 显示"上下文占用 X%"；一旦发生裁剪要提示"已省略最早 N 条消息"，否则用户会以为模型失忆 |
| **系统提示自身超预算** | 要有明确降级策略（提示用户改预设 / 压缩世界书 / 报错），不能静默截断 |
| **世界书与历史统一分配** | 现在世界书按百分比抢预算、历史无上限 → 应纳入同一个总预算 |
| **不碰存档** | 裁剪只作用于"发出去的副本"；存档永远全量 |

#### 实现位置建议

在 `PromptBuilder.buildMessages()` 内、`systemBlock` 与 `history` 都就绪之后插入一步 `_trimHistoryToBudget(history, budget)`，并返回裁剪统计（省略条数 / 估算 token）供 UI 提示。**不依赖 D1–D6，可独立实施。**

#### 酒馆的具体实现（对照参考）

| 机制 | 酒馆怎么做 | 我们该不该抄 |
|---|---|---|
| **两个独立设置** | 「**上下文长度（token）**」= 作为提示词发给 API 的最大 token 数，**不含响应长度**；「**响应长度（token）**」单独设置。二者相加不能超过模型真实窗口 | ✅ 抄。我们现在只有 `maxContext` 且只喂世界书 |
| **裁剪判定** | 按 token 预算装配提示词，**从最新一条往回保留**，超出部分不发送 | ✅ 抄（这是核心算法） |
| **可观测性①：虚线** | 聊天界面有一条**虚线上下文边界**，虚线以上的消息不会发给 AI | ✅ 强烈建议抄（我们的"已省略 N 条"提示可用类似形式） |
| **可观测性②：提示词分项** | 每条回复的三点菜单里有 **Prompt Itemization（提示词分项）**，可查看这次实际发出去的内容构成 | ✅ 建议抄（调试与用户信任都靠它） |
| **世界书单独预算** | 世界信息有独立的「**Context % / Budget**」（占上下文的比例），并提供**溢出告警** | ✅ 抄。我们现在世界书按百分比抢预算、历史无上限，二者需纳入同一总量 |
| **Chat History 是提示词条目** | 「聊天历史」在提示词管理器里是一个**固定条目**，可以**整体关闭**，也可调整在提示词中的位置/深度 | ✅ 部分抄（至少要能控制历史插入点与开关） |
| **超出硬截断的补偿** | 内置 **Summarize 扩展**：把较早对话总结成一份滚动摘要并按位置注入；另有向量存储检索、第三方 Smart Context 等 | ⭕ 可后置。属"长期记忆"能力，不是止血项 |
| **单条消息排除** | `/hide` 可把某条消息排除出上下文（**不删除消息**） | ⭕ 可后置 |
| **计数精度** | 用 tokenizer 估算；Text Completion 有 token padding 纠偏，**Chat Completion 无 padding**，所以同样要靠"安全余量" | ✅ 抄思路：估算 + 余量，或直接用上游 `usage` 真值 |
| **解锁上限** | 预设里有 `max_context_unlocked`（允许填入超过模型已知上限的上下文长度） | ⚠️ 我们内置预设里也有这个字段，需注意别把它当权威上限 |
| **不碰存档** | 被裁掉的消息**仍在存档里**，只是不发送 | ✅ 必须抄（= D5 的同一原则） |

参考来源：[酒馆中文文档·通用设置](https://sillytavern.wiki/usage/common-settings/)（上下文长度/响应长度/虚线/提示词分项）、[Common Settings](https://docs.sillytavern.app/usage/common-settings/)、[提示词管理器](https://sillytavern.wiki/usage/prompts/prompt-manager/)、[World Info budgeting](https://docs.sillytavern.app/usage/core-concepts/worldinfo/)、[Summarize 扩展](https://docs.sillytavern.app/extensions/summarize/)、[Tokenizer guidance](https://docs.sillytavern.app/usage/prompts/tokenizer/)、[SillyTavern Context Size 实践指南](https://thredly.io/sillytavern-context)（辅助来源）。

> 一句话：**酒馆的"裁剪"= 一份 token 预算 + 两个独立设置 + 从新往旧保留 + 虚线/分项两处可观测 + 世界书单独预算；硬截断之外的"长期记忆"交给 Summarize 等扩展，而不是改裁剪算法。**

## 9.3 重要精化：D5 不是"存档只存原文"，而是"三态分离"

核对源码后发现，**酒馆的默认正则（两个 only 都不勾）会直接改写聊天记录本体**：
- AI 输出：`cleanUpMessage`（`script.js:6422`）→ **写回 `chat[messageId].mes`**（`script.js:3624`，流式期间逐 tick 写）；
- 用户输入：`script.js:5816`；
- 官方 UI 文案也写明默认脚本 *"alter the chat file directly and irreversibly"*。

所以精确的模型是**三态**，而不是"存原文 + 显示副本"：

| 态 | 内容 | 由谁决定 |
|---|---|---|
| **存档态**（= 进上下文的历史） | 原始输出经**默认脚本**（两个 only 都不勾）改写后的文本 | 落库路径（无标志） |
| **显示态** | 存档态 + **`markdownOnly`** 脚本，每帧现算，**永不入档** | `messageFormatting`（`isMarkdown: true`） |
| **prompt 态** | 存档态 + **`promptOnly`** 脚本，组装时现算，**永不入档** | 组装 prompt（`isPrompt: true`） |

**对 D5 的修正**：原表述"存档只存原文"过于严格，会与酒馆不一致。正确目标应是——
> **把「默认脚本」与「仅显示脚本」分开：样式类脚本一律用 `markdownOnly`，其产物永不进存档与上下文；默认脚本照旧可以改写存档（与酒馆一致）。**

这样做同时满足三个目标：① 与酒馆完全一致（预设/正则可直接互换）；② HTML/样式标记不会污染存档与上下文（因为样式脚本必须勾 `markdownOnly`）；③ 用户仍有"真的想改存档"的能力（不勾）。UI 上必须照抄酒馆那两个复选框及其文案，否则用户无从判断脚本会写进存档。

**落地需要补的三处调用点**（对应 9.2 表格）：
1. **渲染态**：在渲染管线中对每条消息跑 `applyRegexScripts(mes, scripts, AI_OUTPUT/USER_INPUT, { isMarkdown: true, depth })`——这是 `markdownOnly` 生效的唯一途径；
2. **prompt 态**：`PromptBuilder` 组装 history 时对每条消息跑 `{ isPrompt: true, depth }`；
3. **落库态**：保持现状（无标志），并修正 `PresetImporter.ts:90` 的回落 bug。

**对我们的三个"严重项"（与前面判断一致，此处附带可排期证据）**：
1. **裁剪缺失**：`maxContext` 只喂世界书（`PromptBuilder.ts:88`），历史全量 push（`:215/:227`），请求体只有 `max_tokens`（`client.js:421/590`）→ **长对话今天就必然超上下文或被模型端静默截断**（唯一"功能已经坏了"的问题）。
2. **静默丢档**：`conversationManager.save()` 把异常吞成 `console.error` + `return false`（`:75-78`），调用方不看返回值（`chat.vue:368`）→ 超 H5 5MB 配额即**无声丢档**；且**无防抖**，每次消息变更都整份序列化（`chat.vue:470/482/554/597/609/660/714/729`）。
3. **可观测性为零**：只有 `DEBUG_ENABLED` 控制台打印，用户侧看不到"这次发了什么、哪些消息进了上下文"→ 无法验证第 1 条裁剪是否正确，也无法回答"为什么角色忘了前面的事"。

**明确"未找到"**：①酒馆服务端源码；②酒馆任何"保证首条消息保留"的特例；③我们项目中任何对话分页/"加载更多"实现；④我们项目中任何摘要生成注入或向量/记忆检索代码。

## 9.5 三块合起来：酒馆的设计原则（一句话各一条）
1. **流式**：**协议解析 → 帧率节流 → 只重写当前那一条**；渲染正确性优先于性能，靠 30fps 兜住成本。
2. **正则**：**一个引擎 + placement 路由 + 三态（存档/显示/prompt）**；样式类脚本必须走 `markdownOnly`，其产物永不入档。
3. **存储**：**大对象不进 localStorage**——聊天去服务端、派生缓存去 IndexedDB、localStorage 只放琐碎设置；长聊天靠**渲染只取最近 N 条 + 上下文按 token 预算从新往旧保留**两道闸门。

**我们三块共同缺的，其实是同一个东西：没有"分层"。** 流式缺节流层、正则缺显示层、存储缺派生层。三处的修法在结构上是同构的：**把"真源"与"派生"分开，并给派生加一道有预算的闸门。**

## 9.6 三项待澄清说明（D11 / D13 / D14）

### 9.6.1 D11：存档加 "header" 到底有什么用

酒馆的聊天文件**首行不是消息，而是一个 header**（`chat: [chatHeader, ...trimmedChat]`，`script.js:7368-7383`），里面装的是 `chat_metadata`——**"属于这场对话、但不属于任何一条消息"的数据**。实测它在酒馆里装了这些：

| 字段 | 用途 | 证据 |
|---|---|---|
| `integrity` | 对话身份 uuid，**保存冲突时用来要求用户确认 OVERWRITE** | `script.js:7607`、`:7394-7414` |
| `tainted` | 该对话被扩展/工具改写过的安全标记 | `script.js:1659/4288/5846/8131/9323` 等 |
| `lastInContextMessageId` | 上下文边界（虚线画在哪） | `script.js:6041` |
| `variables` | **对话级变量**（区别于全局/局部变量） | `variables.js:24/54/270` |
| `timedWorldInfo` | **世界书限时效果（sticky/cooldown）状态** | `world-info.js:561` |
| `persona` | 本对话锁定使用哪个 Persona（"聊天锁"） | `personas.js:936/1088/1423` |
| `scenario` / `mes_example` / `system_prompt` | **对话级覆盖**角色卡字段 | `script.js:8991-8993` |
| `attachments` | 附件 | `chats.js:1304/1760` |
| `main_chat` | 分支/检查点的父对话链接 | `bookmarks.js:121` |
| `chat_id_hash` | 供宏使用 | `macros.js:323` |

**关键认识：我们其实已经有 header 了，只是没分开。** 我们现在的存档对象是：

```json
{ cardId, cardName, presetId, regexPresetId, personaId,
  messages:[...], localVariables, worldInfoState, trpgState, updatedAt }
```

其中 `presetId / regexPresetId / personaId / worldInfoState / localVariables / trpgState` **就是我们的 chat_metadata**（`worldInfoState` 正对应酒馆的 `timedWorldInfo`）。所以 D11 不是"引入新概念"，而是**把已有元数据显式收进一个 `header` 字段，并补两样现在没有的东西**：

| 补什么 | 解决什么 |
|---|---|
| `schemaVersion` | 将来改存档格式（D8 迁 IndexedDB、D5 三态）时，**能识别并迁移老档**；否则只能靠猜 |
| `revision` / `chatId` | **跨设备同步（D6 的后续）时的冲突检测**——没有版本号就无法判断"哪份更新" |
| 元数据与消息分离 | 消息可以将来**分片/分页存储**（D8），header 保持小而稳定 |

**一句话**：header = 对话级元数据 + 版本号 + 修订号。它的价值**现在不大，在"改格式"和"跨设备"这两件事上才体现**。若你想推迟，也可以只加 `schemaVersion` 一个字段（成本极低），其余等做同步时再说。

### 9.6.2 D13：为什么"直接取上游真实计数"不能完全替代本地计数

⚠️ **有一个前置限制必须知道**：

> **上游的 `usage`（prompt_tokens / completion_tokens）是在响应「结束时」才返回的**（流式下是最后一个 chunk）。

而**裁剪必须发生在"发送之前"**——你要先知道历史有多少 token，才能决定丢多少条。所以：

| 用途 | 能否用上游 usage |
|---|---|
| **发送前裁剪历史** | ❌ **不能**（还没发，拿不到） |
| 监控页/用量统计 | ✅ **能**，而且最准、零成本 |
| **校准本地估算** | ✅ **能**（拿真实值反推比例，自动纠偏） |

所以 D13 的**简化正确形态**是：

1. **裁剪用本地估算**：项目里已有 `estimateTokenCount`（纯正则，`tokenizer.ts:15-22`），够快也够用；
2. **统计用上游 usage**：流式请求加 `stream_options: { include_usage: true }`，取最后一个 chunk 的 `usage`；
3. 不做酒馆那套"影子预算 + padding + 图片 85 token"的复杂度。

**落地时的两个通道差异（已核验）**：

| 通道 | 能否透传 `stream_options` |
|---|---|
| 用户自配 Key（`/api/chat/completions`，http-proxy-middleware 转发） | ✅ 请求体原样透传，可直接加 |
| 内置测试通道（`/api/chat/test`） | ⚠️ **会被丢掉**——`PASSTHROUGH_PARAMS` 白名单（`server.js:376-379`）只有 8 个采样字段，**不含 `stream_options`**，需补进白名单或由服务端自行设置 |

（顺带：这条也解释了为什么现在"生成结束后用真 tiktoken 重算整段 prompt"——因为拿不到上游 usage。补上 `stream_options` 后，这个卡顿可以整体删除。）

### 9.6.3 D14：什么是"上下文可观测性"

问题是：**一旦开始裁剪，用户会突然觉得"角色失忆了"，但界面上什么都看不出来。** 开发者也无法验证裁剪是否按预期工作。

"可观测性"就是**把"这次到底发了什么"显示出来**。分三档，按成本递增：

| 档 | 内容 | 成本 | 价值 |
|---|---|---|---|
| **最小版** | 生成完成后在消息下方显示一行：`输入 XXX tokens · 输出 YYY tokens · 本次省略最早 N 条消息` | 很小 | 用户能理解"为什么它忘了"；你能验证裁剪生效 |
| **中档** | 在消息流里画一条**虚线**标出"从此往上不发送"（酒馆的 `.lastInContext`，`script.js:6024-6042`） | 小 | 直观；但注意酒馆只在 Text Completion 路径有，OAI 路径没有 |
| **完整版** | 酒馆的分项面板：堆叠柱状图（System/World Info/Chat History/Extensions…）+ 逐项 token 表 + Show Raw Prompt + **与上一条的 diff** | 中大 | 调试提示词注入/世界书抢占预算的利器 |

**建议**：先做**最小版**（它同时也是"裁剪功能"的验证手段），中档视图可选，完整版等有需求再说。

> 关联：这也正是前面 5.10 里"必须可观测"那一条的落地形态。

## 9.7 D14 落地设计要点（完整版分项面板）

### 入口与形态（已定：藏进现有按键，独立弹窗）

- **入口**：不新增主界面控件。放在**「设置」页**（`src/pages/settings/settings.vue`）里一个条目/按钮，例如「**上下文详情**」；聊天页也可考虑长按 AI 消息 → 菜单里加一项「查看本次上下文」。
- **形态**：**独立弹窗/页面**，不要内嵌在聊天流里（避免打扰阅读、也避免移动端挤压）。
- **默认只读**：纯展示，不可编辑（编辑提示词另有入口）。

### 弹窗内容（对齐酒馆，但按移动端重排）

| 区块 | 内容 |
|---|---|
| ① 总览 | `本次预算 = maxContext − 预留回复`、`实际用量 / 预算`（百分比 + 绝对值）、`是否发生裁剪` |
| ② 占比图 | 各段占比（系统提示 / 世界书 / 作者注 / 深度注入 / 聊天历史 / 本次用户消息 / 预留回复）。酒馆用堆叠柱状图，**移动端建议改为横向条形列表**（每条一行：色块 + 名称 + token + 占比），更易读 |
| ③ 逐项表 | 每项一行：名称、token、占比；**超预算或异常项高亮**（红色） |
| ④ 聊天历史明细 | `进入上下文 N 条 / 共 M 条`，**被省略的最早 K 条**可展开查看标题预览 |
| ⑤ 原始 prompt | 可折叠的纯文本块 + **一键复制**（长文本默认折叠） |
| ⑥ 与上一条对比 | diff 高亮（新增/删除），用于排查"这轮为什么变长了" |

### 易读性要求（移动端优先）

1. **中文标签 + 一行一事**，不做密集表格；窄屏用"名称 / 数值"两列布局。
2. **数值双列**：同时给 `token 数` 与 `占预算 %`，避免用户心算。
3. **颜色与分区一一对应**：占比图色块与逐项表行首色块同色。
4. **裁剪要显眼**：发生裁剪时置顶一条提示条（"本次已省略最早 K 条消息"），并可点开看是哪几条。
5. **长文本默认折叠**：原始 prompt、被省略消息预览都默认收起。
6. **对齐字号/断点**：沿用现有 settings 页的字号与间距规范，避免小屏溢出。
7. **跨端降级**：必须以 uni-app 的 `view/text` 实现（不用 DOM/innerHTML），小程序端只做降级展示（D3 保持现状）。

### 数据来源与存储（与 D8 配套）

- 需要在**每次生成时**把"这次实际发送的构成"做成**快照**：各段名称 + token + 总预算 + 实际用量 + 历史条数 + 被省略条数 + 原始 prompt + 时间戳。
- **存储位置**：**IndexedDB**（对应酒馆把分项存 `localforage` 的 `SillyTavern_Prompts`，按 chatId 组织，`itemized-prompts.js:15/46-52`）；**不要进 localStorage**（快照含原始 prompt，体积大）。
- **保留策略**：只保留最近 N 条（建议 20），超出滚动删除，避免无限增长。
- 这条依赖 **D8 落地**；若 D8 未完成，可先只在内存中保留"最近一次"，功能可用但不持久。

## 9.8 reasoning（思考）的两种来源与酒馆处理方式（Q5 分析）

### 9.8.1 关键认识：思考有**两种来源**，不能混为一谈

| 来源 | 形态 | 例子 |
|---|---|---|
| **① API 原生字段** | 上游在 **delta 的独立字段**里返回，与正文并列 | DeepSeek `delta.reasoning_content`；OpenAI o 系 `delta.reasoning` / `reasoning_content`；Claude `delta.thinking`；`choices[0].thinking`；Mistral `content[0].thinking[0].text`（酒馆 `sse-stream.js:257-315` 识别这 5 种） |
| **② 文本编码（COT 写在正文里）** | 模型把思考**当成正文的一部分**吐出来，靠**前后缀定界符**区分 | 角色卡/预设里教模型用 ` thinking…<｜end▁of▁thinking｜>`、`<analysis>…</analysis>`、`[思考]…[/思考]` 等包裹 |

**"角色卡内置 COT"属于第 ② 类**：从 API 的角度看，那些文字就是 `content`（正文）——**上游根本不知道那是思考**。只有它带了可识别的定界符，前端才能事后把它"切出来"当成思考展示。

### 9.8.2 我们现在的实现是错的（且错法比"混为一谈"更糟）

```js
const delta = json?.choices?.[0]?.delta?.content || json?.choices?.[0]?.delta?.reasoning_content;
```
（`src/utils/llm/client.js:520`，`_parseSSEText` 内 `:678` 同款）

`||` 是"**真值取胜**"，所以：

| 情况 | 后果 |
|---|---|
| 该 chunk 只有 `reasoning_content`（思考阶段，`content` 为空串） | ❌ **思考被当成正文显示**，并被写进消息、写进存档、写进下一轮上下文 |
| 该 chunk 同时有 `content` 和 `reasoning_content` | ❌ **思考被静默丢弃**（`content` 为真，右侧不求值） |
| 模型不返回思考 | 无影响 |

也就是说：**不是"合并"，而是"二者只能活一个"**——顺序相关且有损。此外 `thinking: {type:'disabled'}`（`client.js:398-400`）是我们为了绕开这个问题而**直接关掉了思考能力**。

### 9.8.3 酒馆怎么做的（六层）

| 层 | 做法 | 证据 |
|---|---|---|
| ① 协议识别 | SSE 解析层对 5 种 reasoning 字段打 `reasoning: true` 标记 | `sse-stream.js:257-315` |
| ② 分流累积 | `state = { reasoning, images, signature, ... }`，思考进 `state.reasoning`，正文单独返回——**两个缓冲** | `openai.js:3074/3128-3211`（DeepSeek 分支 `:3156-3159`） |
| ③ 状态机 | `ReasoningHandler` 维护 `ReasoningState`（None/Thinking/Done/Hidden）+ 起止时间 → "Thinking… / Thought for N seconds" | `reasoning.js:256/434-451` |
| ④ 存储 | 思考存 **`message.extra.reasoning`**（**独立字段**，永不混进 `mes`） | `reasoning.js:409/1506/1555` |

### 9.8.4 如果模型没有 `reasoning_content` 字段怎么办

- **不显示折叠块**（不要渲染空块），也不要有任何占位；界面上与现在完全一致。
- 若该模型属于"内部思考但不外露"，用户只是看不到思考，功能不受影响。
- 若用户想在这种模型上看到思考，**只有第 ② 类（文本编码）能提供**——需要角色卡/预设要求模型用定界符输出，再靠前后缀解析切分。

| # | 做什么 | 说明 |

## 9.9 文本 COT 解析（auto_parse）与正则的关系

### 9.9.1 先澄清：酒馆的 `auto_parse` **本身就是用正则实现的**

```js
const regex = new RegExp(`${(strict ? '^\\s*?' : '')}${escapeRegex(template.prefix)}(.*?)${escapeRegex(template.suffix)}`, 's');
```
（`reasoning.js:1430`）——它就是"把用户配置的前后缀拼成一个正则"，再对消息文本做匹配。

所以问题的答案不是"不能用正则"，而是：**这段逻辑为什么被放在引擎层，而不是交给用户的正则脚本系统。**

### 9.9.2 为什么它不能（完全）由"正则脚本"承担

关键差别在**引擎契约**：

| 能力 | 正则脚本（`getRegexedString`） | 引擎层的 auto_parse |
|---|---|---|
| 契约 | **`string → string`**，只能改文本 | 可以**改字段**（把命中的内容从 `mes` **搬到** `extra.reasoning`） |
| 能否把内容分流到另一条通道 | ❌ 不能。最多把思考**删掉**或替换成别的文本 | ✅ 能——这是"独立折叠块 / 独立开关 / 独立正则 placement"的前提 |
| 流式**未闭合**时 | ❌ 匹配不到（`(.*?)` 需要后缀）。于是思考会以原文形式在流式期间露出来，闭合那一刻再"跳"一下 | ✅ 有状态机：prefix 一到就切换状态、`mes` 置空，流式期间**不泄露原文**（`reasoning.js:460-507`） |
| UI 语义 | ❌ 无（折叠块、"Thought for N 秒"、`auto_expand`、`/reasoning-collapse`） | ✅ 能驱动 |
| 与 **API 原生思考**合流 | ❌ 不能——两条来源无法汇入同一个折叠块 | ✅ 能，两条来源都进 `extra.reasoning` |
| 参数化 | 每个用户自己写一条 | ✅ 可配置前后缀模板（`/reasoning-template DeepSeek`），并可随内置换掉 |

**一句话**：正则脚本是"**改字**"的工具，思考折叠需要的是"**分流 + 状态 + 结构**"的能力。把 auto_parse 写成正则只是它的**实现手段**，不是它的**能力边界**。

### 9.9.3 我们该怎么做（三种选择）

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A 纯正则** | 用户自己写一条正则把思考删掉/替换 | 零开发 | 没有折叠块；流式期间仍会露原文并跳变；无法与原生思考合流 |
| **B 内建切分（酒馆式）** | 前后缀可配，命中内容搬进 `reasoning` 字段 + 折叠 UI | 体验完整、可与原生思考合流、流式不泄露 | 需要开发（状态机 + UI） |
| **C 内建切分 + 暴露给正则（推荐）** | 在 B 的基础上，把切出来的 `reasoning` 也交给 `placement=REASONING` 的正则处理 | 既能兜住角色卡 COT，又给用户二次加工的自由；**与酒馆完全一致** | 需要先有 `reasoning` 通道（即 9.8.5 的第 1、2 件） |

**推荐 C**，但它**必须晚于**"分流 + 独立字段"（9.8.5 的 1、2 件）——因为 B/C 都建立在"存在 reasoning 通道"之上。

## 9.10 「系统正侧」的落地位置（D15）

- **形态**：**代码内置的正则脚本集合**（TS 常量），**不是** `/assets` 下的 JSON，也**不落盘**（与 D7 一致）。
- **内容**：首选是「台词识别」（D1 把现有硬编码翻译成的那条正则），以及将来其它默认规则。
- **选择语义**：它等价于「**会话正侧层**」的**默认值**——
  - 用户没选其他正侧文件 → 生效；
  - 用户选了其他正侧文件 → **被替换（不叠加）**。
- **UI 提示**：在"选择正侧文件"处把「系统正侧」列为默认项；用户切换到其他文件时给出提示（"系统正侧将不再生效"），避免用户"以为台词高亮还在"。

### 9.11.2 打字机的适用范围（含一个必须修的判定 bug）

| 场景 | 期望行为 |
|---|---|
| H5 + 流式开启 + 上游支持流式 | **真流式**，无打字机 |
| 流式关闭（用户预设里关掉） | **打字机**（按帧批量，速度快） |
| **小程序端**（上游不支持流式） | **打字机**——不能整段一次性出现 |

**⚠️ 现状与期望不符（必须修）**：`MessageProcessor.ts:118` 用 `streamEnabled = !!preset.generationParams?.stream` 决定"要不要走打字机"，而小程序端 `client.js:337-347` 在流式分支里是**一次性拿到全文后只回调一次** `onChunk(full)`。于是：**系统预设开了流式 → 小程序端判定为"已流式" → 跳过打字机 → 整段一次性出现**。

**修正原则**：把判定依据从"**预设是否开了流式**"改为"**这次是否真的发生了增量流式**"——
- 由 `client` 返回/上报"本次是否为真流式"（或统计 `onChunk` 的增量次数）；
- **真流式** → 不打字机；**否则**（含小程序一次性返回）→ 一律走打字机。

这样三种场景才对得上上表，且与酒馆"非流式不做假打字机"的差异是有意为之（我们要在小程序端保留打字机观感）。
