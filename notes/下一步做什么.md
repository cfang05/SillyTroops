# 下一步做什么

本文档只回答三个问题：**下一步做什么、怎么做、怎么算做完了。**

不写指标、不写泳道、不写方法论。一件事做完再做下一件。

---

## 总览

一共五步，按顺序做。每一步都有明确的验收动作，验收不过就不进入下一步。

| 步骤 | 做什么 | 预计工作量 |
|---|---|---|
| 第一步 | 搞清楚现在到底还差什么 | 1 天 |
| 第二步 | 补上让老角色卡能正常用的缺口 | 1–2 周 |
| 第三步 | 让角色有自己的记忆 | 2–3 周 |
| 第四步 | 让角色能去别的世界 | 2–3 周 |
| 第五步 | 让多个角色一起出场 | 3–4 周 |

第三步做完就可以上线了。第四步做完是真正的差异点。第五步是玩法扩展。

# 第一步：搞清楚现在到底还差什么

## 为什么要做

`notes/兼容性差距清单.md` 说"标记提示词不填充""注入位置语义相反""宏系统只支持单层""作者注完全缺失"，判定这些是最致命的缺陷。

但我去看代码，这四条**都已经修好了**。

这份文档已经过期。按照它继续干活，会把改好的东西再改一遍。所以第一步不是写代码，是把这份文档核对一遍。

## 怎么做

拿一份真实的酒馆角色卡，从导入开始，走完整个流程：

导入角色卡 → 新建对话 → 发一句"你好" → 看回复 → 看渲染 → 继续聊十轮

每一步都记录：能不能用、哪里不对、哪里报错。

重点核对这几处（这些是差距清单里判定为"致命"的）：

1. **角色卡的人设有没有真的进到提示词里。** 看 `src/engine/PromptBuilder.ts`，找到 `markerContents` 那一段。角色卡里的描述、性格、场景、对话示例，都应该被填进去。
2. **预设里的注入位置有没有反。** 看同一个文件里 `item.injectionPosition === 1` 那一行。等于零是在系统提示里按顺序排，等于一是按深度插进对话历史。跟酒馆的语义对比一下。
3. **对话示例有没有当成少样本例子喂给模型。** 找 `_formatDialogueExamples` 这个函数。
4. **宏能不能用带参数的写法。** 看 `src/engine/VariableEngine.ts`，试一下 `{{random::甲::乙}}` 这种。
5. **世界书能不能正常触发。** 找一张带世界书的卡，说一句能命中关键词的话，看词条内容有没有进提示词。

## 算做完了的标准

产出新的 `notes/兼容性差距清单-新.md`，里面写清楚：

- 每一条旧结论，标注"已修好"还是"确实还缺"
- 确实还缺的，按"影响能不能用"排个顺序
- 区分开两类：一类是"不改就没法正常聊天"，一类是"不改也能用，只是不够像酒馆"

**这一步不写任何功能代码。**

# 第二步：补上让老角色卡能正常用的缺口

## 为什么要做

后面三步全部建立在"角色卡能正常用"之上。这一步没做完就往下走，后面出的所有问题都分不清是谁的错。

## 怎么做

只做第一步里分出来的第一类——**不改就没法正常聊天**的那些。

从代码看，已知确定还缺的是这几项：

| 缺的东西 | 在哪个文件 | 具体是什么 |
|---|---|---|
| Markdown 渲染 | `src/engine/BlockParser.ts` | 现在只认游戏标签（选项按钮、摘要卡片、时间卡片等），不认粗体、斜体、列表、引用、`*动作描写*`。角色卡里这些写法到处都是，不渲染的话聊天内容看着是乱的 |
| 真实流式输出 | `src/engine/MessageProcessor.ts` | 现在是打字机效果模拟出来的，不是模型那边真的一个字一个字传过来 |
| 最大生成长度会挤爆上下文 | 预设编辑页面 | 现在的情况：如果用户把最大生成长度设成 8000，而上下文窗口上限还是 4096，算下来留给历史消息的空间是负数，结果一条历史都发不出去，表现是"角色突然失忆"。要在预设编辑页直接拦住这种配置，不让保存 |

另外顺手修一个数字不一致的问题：

- `src/engine/PromptBuilder.ts` 里裁剪对话历史时，用的是估算出来的 token 数（按经验公式：中文字算一个字一个 token，英文单词算一点三个 token）。
- 而界面上给用户看的上下文占比，用的是另一套数字。
- 结果是：**决定丢哪条历史的依据，和给用户看的数字，对不上。**
- 改成两者用同一套即可。

第一步里发现的、属于"不改也能用"的那一类，不要在这一步做，记下来，以后有空再说。

## 算做完了的标准

1. 拿十张真实的老角色卡，每张都走完：导入 → 新建对话 → 聊十轮 → 看渲染。
2. 十张全部不需要任何手动修补就能正常使用。
3. Markdown 能正常显示：`**粗体**`、`*斜体*`、列表、引用、`*动作描写*` 都有正确样式。
4. 模型回复是真流式，不是一个字一个字模拟出来的。
5. 最大生成长度设置得过大时，预设编辑页会提示并且不让保存。

**十张卡有任何一张卡住，就继续修，不进入第三步。**

# 第三步：让角色有自己的记忆

## 为什么要做

这是整个项目跟酒馆拉开差距的第一件事。

酒馆里，角色卡是个死文件——聊完就没了，换个对话全部清空。我们要做的是：**角色是个活的东西，它记得跟你发生过什么，而且这些记忆不会因为换了个对话就消失。**

做完这一步就可以上线。因为这时候已经有酒馆给不了的东西了。

## 怎么做

分四件事。

### 1. 数据存哪

现在的对话记录存在浏览器本地（IndexedDB）。角色记忆不能这样存。

原因：用户换个手机、清一下浏览器缓存，角色的成长就全没了。这跟"角色是活的"这个卖点直接冲突。

所以记忆必须存在服务器。你已经有 PostgreSQL 数据库（Neon），加表就行。

### 2. 数据结构设计

记忆分两块，**不要全用向量检索**。

| 类型 | 存什么 | 举例 | 怎么用 |
|---|---|---|---|
| 结构化记忆 | 精确的事实和数值 | 当前情绪、对你的好感度、经历过的事件列表、它怕什么、它答应过你什么 | 每次生成回复时**全部塞进提示词** |
| 向量记忆 | 很久以前的对话片段 | 上个月聊过的某件事的原文 | 按语义相似度**检索出相关的几条**再塞进去 |

为什么结构化记忆不能省：像"它怕水""它欠你 300 金币""它答应过不杀生"这种，用向量检索查不准——向量检索查的是"意思相近"，不是"精确匹配"。而且角色卡大多是英文，你输入是中文，跨语言检索命中率会很难看。

结构化记忆才是"人设不崩"的保障。

另外：**结构化记忆塞进提示词之前，必须限制长度。** 建议给个上限（比如 800 个 token）。超了就压缩成摘要，不能任由它无限变长。否则聊得越久，提示词越长，最后角色被一堆琐碎记忆淹没，反而更不像自己。

### 3. 每一轮对话要做什么

```
玩家发一句话
  ↓
拼提示词：角色人设 + 世界背景 + 最近的对话 + 该角色的结构化记忆
  ↓
调模型，生成回复
  ↓
把回复给玩家看
  ↓
后台解析这轮对话，抽取事件（发生了什么、情绪有没有变化、好感度有没有变）
  ↓
写回数据库
```

关键：**写回数据库这件事必须由代码做，不能让模型直接改数据。**

模型只负责生成一段文字，然后由代码去解析这段文字、决定要改什么。模型永远不碰数据库。这条后面每一步都适用。

### 4. 界面上能看到什么

至少要能看到记忆确实在起作用，不然用户不知道这个东西存在。

最小版：角色详情页里显示当前情绪、好感度、最近三条经历。

## 算做完了的标准

1. 跟一个角色聊二十轮，中间明确告诉它几件事（比如"我怕狗""我住在北京"）。
2. 关掉页面，重新打开，接着聊。
3. 问它"我之前跟你说过什么"，它答得出来。
4. 换个浏览器或者换台设备，登录同一个账号，记忆还在。
5. 记到第三十轮的时候，翻回第十轮时它说过的信息，它还记得。
6. 提示词里的记忆部分，长度不会无限涨——到上限之后是压缩，不是越堆越多。

**第 3 条和第 4 条过不了，就不进入第四步。**

# 第四步：让角色能去别的世界

## 为什么要做

这是整个项目真正的差异点，也是别人抄不走的东西。

**同一个角色，今天是中世纪的骑士，明天去科幻世界，后天到现代都市。它还是它，说话方式不变、性格不变、记得之前的事，但它不会被新世界的规则搞崩。**

酒馆做不到这件事。酒馆里角色卡绑定自己的世界设定，换了世界，角色就变形了。

## 怎么做

### 1. 先把设定拆成两半

一张角色卡里，其实混着两种东西：

| 类型 | 内容 | 举例 |
|---|---|---|
| 角色私有 | 人设、性格、说话方式、个人偏好、专属记忆 | "他是个沉默寡言的骑士，说话简短，讨厌说谎" |
| 世界公共 | 地图、势力、时代背景、规则 | "这个大陆有七个王国，魔法是禁忌" |

**关键：不要动原来的角色卡。**

不要导入的时候就把角色卡拆开重存。因为自动拆分一定会出错，出错了用户还没法回头。

正确做法：角色卡原样不动存着，另外存一张对照表，记着"这张卡的哪个字段属于私有、哪个属于公共"。生成提示词的时候，根据当前世界的设定，决定哪些字段用角色卡自己的、哪些被世界卡覆盖。

这样拆分错了可以改，用户不满意可以手动调，而且完全不影响导入。

### 2. 冲突检测

角色带着自己的设定进入一个新世界时，检查有没有打架的地方。

举例：角色设定是"魔法骑士"，进入的科幻世界里"魔法不存在"。

这一步用模型来判断。做法是把角色私有的设定和世界的公共设定一起给模型，让它列出冲突项。

### 3. 冲突怎么处理

给用户三个选项，不要替他决定：

| 选项 | 效果 | 举例 |
|---|---|---|
| 保留 | 角色设定完全不变 | 它坚持自己是魔法骑士，哪怕在这个世界说不通 |
| 适配 | 改成符合新世界的说法 | "你总爱幻想自己是魔法骑士" |
| 混合 | 用户自己调比例 | 介于两者之间 |

界面上让用户随时能改。默认用哪个由用户自己设。

## 算做完了的标准

1. 找一张人设很强的角色卡（比如中世纪骑士），依次进入三个世界观完全不同的世界卡（奇幻、科幻、现代都市），每个世界聊二十轮。
2. 每个世界聊完，停下来问自己三个问题：
   - **它还是原来那个角色吗**（性格、说话方式、行为逻辑）？
   - **它还记得之前那个世界发生的事吗**？
   - **它在新世界里显得突兀吗**，还是自然融入了？
3. 三个世界的三个问题，如果"它还是原来那个角色吗"这一条明显不成立（角色被新世界带跑了），这一步就还没做完。
4. 冲突检测要能真的检出问题：故意构造十个角色设定和世界设定打架的例子，至少能检出八个。
5. 三档处理策略都要真的有效果——选"保留"就真的不动，选"适配"就真的改成新世界的说法。

**第 3 条是这一步的核心。这条不过，不要进入第五步。**

# 第五步：让多个角色一起出场

## 为什么要做

到这一步，一个角色已经能跨世界了。这一步是让多个角色同时出场，互相说话，组建小队。

## 怎么做

### 1. 每个角色独立推理

三个角色在场，不是把三个人的设定拼一起发一次请求。而是**发三次请求**：

```
角色甲：它自己的人设 + 它自己的记忆 + 到目前为止的对话  → 生成甲的台词
角色乙：它自己的人设 + 它自己的记忆 + 到目前为止的对话 + 甲刚说的话  → 生成乙的台词
角色丙：它自己的人设 + 它自己的记忆 + 到目前为止的对话 + 甲和乙说的话  → 生成丙的台词
```

**必须是这个顺序，不能同时发。** 因为乙要能看到甲说了什么才能接话。

如果三个请求同时发，三个人互相看不见，就会各说各话：

```
（顺序生成，正确）
甲：这船太沉了，我一个人推不动。
乙：那一起推，我数三下。

（同时生成，错误）
甲：这船太沉了，我一个人推不动。
乙：好主意，我去拿绳子。   ← 答非所问，因为乙没看到甲说推不动
```

代价是慢——三个人就是三倍等待时间。如果实测下来一轮要四十秒，就得考虑砍到两个人，或者换个更快的模型。

### 2. 记忆绝对不能串

每个角色只能拿到自己的记忆。这一条由代码保证，不靠人工检查。

做法很简单：所有读记忆的接口，**必须传入角色编号这个参数**。组装甲的上下文时，代码里根本拿不到乙的记忆对象，物理上就不可能串。

要注意区分两件不同的事：

- **甲的私有记忆，乙不该知道** → 靠上面的机制保证，必须做到 100%。
- **乙回应甲刚说出口的话** → 这是正常的，也是你想要的效果。因为对话记录里本来就有甲的话。这不是串记忆。

### 3. 状态回写

每一轮所有角色说完之后，统一解析这一轮发生了什么，更新各个角色的情绪、好感度、经历。

还是那条规矩：**模型只生成文字，写数据库由代码做。**

### 4. 再加一个驻地

一个轻量的场景，用来：集结队员、休整、整理行囊、挑人组队。

**注意：驻地不是一张有固定剧情的世界卡。它是个开放的空场景。**

要区分清楚两件事：

- **驻地卡** = 模板，是静态的、可以导出分享的
- **驻地实例** = 某个人自己的驻地存档，存着队员名单、行囊、任务进度

这两个不能是同一个东西。否则导出的时候你会分不清导出的是模板还是自己的存档。

## 算做完了的标准

1. 三个角色进同一个世界，聊二十轮。
2. **每个角色的说话方式能明显区分开**，不会三个人说话一个味儿。
3. 角色之间能互相接话——甲说完，乙会针对甲的内容回应，而不是各说各话。
4. 角色之间会出现配合或者意见不合，不是三个人轮流自说自话。
5. 检查有没有串记忆：代码层面确认组装甲的提示词时不含乙的记忆。这个写个自动化检查，不靠眼睛看。
6. 聊完之后，每个角色的情绪和好感度都正确更新了，没有张冠李戴。
7. 驻地能正常集结队员、整理行囊、组队进入世界。

**第 2 条和第 5 条过不了，这一步就没做完。**

# 每一步都不要做的事

| 不要做 | 原因 |
|---|---|
| 把界面做得跟酒馆一模一样 | 这是手机应用（宽度限制 480 像素），酒馆是电脑网页。手机上做不出电脑的多栏布局，硬做会两边都不像。**菜单名字和操作习惯跟酒馆一致就够了**，不用管长得像不像 |
| 支持角色卡 V3 格式和素材系统 | 用这个格式的卡极少，做起来麻烦 |
| 做斜杠命令（`/send` 这类） | 只有重度玩家会用，普通玩家点按钮就行 |
| 同时支持对话模式和补全模式 | 只做对话模式 |
| 给微信小程序做新功能 | 小程序已经暂停 |
| 做两套界面 | 只做一套，新功能用开关控制显示 |
| 让服务器承担模型调用费用 | 用户自己配密钥，费用用户出 |

# 每一步都要守的规矩

这七条每个步骤都适用，写代码的时候不要破：

1. **世界的公共状态绝对不能改角色的私有状态。**
2. **模型只生成文字，绝不直接改数据。所有状态变更由代码执行。**
3. **多个角色绝不共用记忆、绝不共用人格，每个都是独立实例。** 用代码断言校验，不靠人工检查。
4. **驻地不写成固定剧情，保持开放。**
5. **新能力全部外挂，不改酒馆原有内核。**
6. **跨角色、跨世界的冲突由中间层消解，不硬覆盖人设。**
7. **写出去的卡片要清掉自己加的字段。** 给酒馆导出的卡，必须把私域标记、记忆库编号这些我们自己的字段删干净。否则酒馆会把它当成扩展字段存下来，再导回来的时候数据就被污染了。

# 现在就开始

第一步只有一件事：**拿一张真实的酒馆角色卡，走完整流程，看看哪里断。**

这是唯一现在就能做、而且必须做的事。其余所有事情都等这一步的结果。
